01

What actually runs

The loop is the whole system. A schedule fires, a database view works out which chunks are runnable for which companies, those become rows in a queue, workers claim them, and each worker collects only its own slice. Finishing a chunk unlocks whatever depended on it — that return edge is what makes the thing walk forward on its own.

02

Where the obvious build breaks

Two details decide whether this survives contact with 504 companies. Both look like implementation trivia and are actually the difference between a pipeline that grinds along unattended and one that needs babysitting.

Fan-out belongs in a table, not in an execution

Splitting to agents inside a single n8n execution keeps every item in one process’s memory, runs the branches serially, and loses everything if the execution dies. Writing queue rows instead costs one table and buys retries, restart survival, and real parallelism.

Findings need their own rows

If every chunk writes back into one JSONB column on the company, twenty-four concurrent chunks read-modify-write the same cell and the last one silently discards the rest. Give each datapoint its own row and the collision cannot happen — the primary key forbids it.

Already true in your database

companies.civ and companies.civ_chunks already exist as jsonb, and civ_chunk_def already holds all 30 chunks with their dependencies. The findings table and the queue are the two pieces missing.

03

Build order

Thirteen working days, five phases. The shape that matters: definitions and infrastructure run alongside the schema work from day one, the three workflows are a single-file critical path, and the chunk implementations fan out wide once the runner exists.

PhaseWhat gets builtDone when
A Findings table with the citation constraint, the run queue, the dependency view, budget guard An insert of an uncited value is rejected by the database
B 134-datapoint catalog loaded and bound to the graph, archetypes, prompts, state statutes 134 rows, zero unbound, 25 discovery questions derived
C Guard, scheduler, chunk runner — the three workflows that make it move One company clears the litigation screen end to end
D The chunk bodies: 8 pure SQL, 3 acquisition, 4 extraction, 10 research Zero citation violations; 9 of 10 quotes found by hand at their URL

04

Start here

  1. Rad configures n8n queue mode — Redis plus worker containers on Hostinger, execution pruning on. It depends on nothing else and it is what turns a week-long pass into an overnight one.
  2. Apply Phase A — four migrations. The gate is a deliberately failing insert: if an uncited value stores successfully, the evidence guarantee is void and nothing after it is worth building.
  3. Load the catalog in parallel — the 134 rows bind to the chunk graph with a single join, because the datapoint codes already match what civ_chunk_def lists as produced.
